## What the new work is

- **eee1c20 "Ship full engine 2.3.2"**: the engine was swapped for a fresh import of **upstream Hookshot's main of about
  2026-11-15** (its tested/ files name main a00c485c / e090cc48, `v3.0.0-rc.4`), relabelled `v2.3.2-reborn`, with
  "hookshot" renamed "ocarina_reborn" in strings and file names. Reborn's own policy files (ocr_*.h, hold_gpu.h,
  commit_room.h, texture_budget.h, ocr_capture_pool.inc, threaded_rendering.h, ocr_view.c, ocr_tunic.c, ...) are
  **byte-identical** to v1.1.3: Reborn re-applied its old patches on the new base. Their own fast-float lifter (nx2/fastfp.py)
  and the gpu/render (WebGPU) tree were **dropped**. Their VALIDATION-1.1.4.md: compile and synthetic tests only; the imported
  suite ran 575 pass / 87 fail / 47 skip; **no playthrough, no GPU visual test, no benchmark**.
- **Reborn's own engine changes in the window** are small: vert+ FOV for pictures narrower than 16:9 (host/oot_fov.c), a
  one-process-per-game-folder lock (host/ocr_instance.h), a device-lost message box, the driver-fault list kept across runs
  only on AMD, their capture pool's buffers made readable by the new mirror-sync pass.
- The rest is launcher/installer: forest launcher theme, new build and start screens, Classic UI download (kuledawg's HUD mod
  from GameBanana), return to launcher after a build, CRT filter rows.
- **No numbers for v1.1.4 itself.** All measurements below are upstream Hookshot's, from its docs/tested and code comments.

So nearly every candidate is **an upstream Hookshot change after our base** (our tree: Mako 4.1.1 = Hookshot a2e65052 plus
picks). The clean source for them is Hookshot's own history on git.magicbean.dev, not Reborn's re-import (renamed strings,
Reborn hunks mixed in). Our tree was grepped for each item below; "missing" means the code and its switch are not in ours.

## Candidates, best first

### 1. HLE sync fixes: Broadcast condition variable, timed/try semaphore acquires, long timeouts — PORT FIRST
- What: `nn::os::BroadcastConditionVariable` handled by the host (left to the guest SDK it signalled a kernel key no host
  waiter sleeps on, so waiters slept until some later Signal: the movie framework's queues, NVIDIA's OS layer);
  `TimedAcquireSemaphore`, `TimedAcquireLightSemaphore`, `TryAcquireLightSemaphore` handled by the host (the SDK versions read
  count words the host never writes); a timed wait over ~24 days no longer wraps the DWORD ms. Also the thread-local object
  cache 1024 -> 4096 entries (comment: obj_lookup 2.2% of game threads outdoors at 1024).
- Where: Reborn engine/host/nn_os_sync.c ~208-216, ~289, 622-634, 1009-1038 (upstream Hookshot). This is Reborn's "fewer missed
  wake-ups" patch note.
- Gain: none claimed; correctness (stalls/hangs where the game broadcasts or times a semaphore wait). Unmeasured.
- Ours: missing (only Signal is host-side; diffed).
- Hardware: none. AMD/Windows: yes. Low-end: helps.
- Default: always on (no switch). Size ~45 lines, host only, no randomizer or lift files.
- Risk: low (a waiter now wakes where it slept before). Check: movies (opening, Deku Tree), Kokiri, a scene load.

### 2. Area-entry hitches from VirtualQuery walks: commit marks + import fence — PORT FIRST (then A/B an area entry)
- What: Windows answers VirtualQuery (and a driver's host-pointer import) by walking the run of same-protection pages; the
  game heap is one multi-GB run, so each new GPU pool import cost tens of ms on the replay thread. (a) `commit_marks`: one
  page every 64 MB of every commit made RWX, so runs end there (8 GB run 18.5 ms -> 0.58 ms in their test); (b)
  `ImportFence`: while vkAllocateMemory imports a host pointer, the page after the range is flipped RWX, then back.
- Where: host/mkw_glue.c ~57-90 (`HOS_COMMIT_MARK_MB`, default 64, 0 off); gpu/vk/import_fence.h (~60 lines) used in
  vk_memory.cpp ~504 (`RX_VK_IMPORT_FENCE`, default on, off with write watches).
- Gain: upstream "90-120 ms hitches on the way to Saria" (hs168); the fence: 6-10 in-play imports at 15-29 ms -> none in play
  on a 6-minute route (RTX 4070 Ti SUPER, NVIDIA 621.24). AMD unmeasured: AMD's driver must also validate the pointer, so
  likely, not proven. HeyListen's audit saw "pool imports up to 36 ms each, 20 of them" at an area entry.
- Ours: missing (neither function nor switch).
- Hardware: Windows only (Linux untouched). No VRAM/PCIe dependence. Low-end: helps (longer walks with more commit).
- Size ~100 lines, host + renderer (no API bump needed). No randomizer files.
- Risk: low-medium: RWX guest pages (nothing executes guest memory; an AV may frown); must stay off with write watches.
  Measure: log "import ... took" lines / worst frames entering Hyrule Field or Kokiri from a save, A/B with the switches.

### 3. No pool import inside an unswizzle upload — PORT FIRST (stutter)
- What: the GPU unswizzle path imported a pool just for one upload (22-25 ms on the replay thread; three when the camera turns
  to the Deku Tree = a 60 ms hitch). Now it uses the GPU path only when an imported pool already holds the range
  (`memory_guest_contained`), else the CPU path (multithreaded from 4 MB, a 15 MB level in a few ms).
- Where: gpu/vk/vk_texture.cpp ~1606-1620, vk_memory.cpp 4098-4106. `RX_VK_UNSWIZZLE_IMPORT=1`: import as before.
- Gain: upstream, one 60 ms hitch at the Deku Tree (hardware not named). Unmeasured on AMD.
- Ours: missing (ours calls gpu_buffer() there, which may import).
- Hardware: any. Size ~25 lines, renderer only. Risk: low (falls back to an existing path).

### 4. Process priority class Above Normal — PORT FIRST (tiny)
- What: `SetPriorityClass(ABOVE_NORMAL)` at start (`HOS_PROCESS_PRIORITY`: 0 normal, 1 above normal = default, 2 high).
  Windows boosts other apps' threads on their window events; with another app's UI busy the game's threads waited.
- Where: host/hos_main.c 83-97.
- Gain: upstream, same route alternated: frames >= 40 ms 6 and 7 vs 17 and 10; gaps >= 28 ms 23/21 vs 34/27 (hs206-209,
  hardware not named). Fits this PC: our first HeyListen A/B was spoiled by Firefox and Discord running.
- Ours: missing. Hardware: Windows. Size ~15 lines. Risk: low (above normal, not high; the shader compile workers inherit it).

### 5. The mirror syncs' pages by a compute pass (RX_VK_MSYNC_PASS) — LATER, but the one to A/B for "memory sync"
- What: the pages a capture holds were copied into the mirror as many small copy regions (1,284 regions in 52 copy batches a
  frame, each read over PCIe in turn); now they go as chunks of the existing write-back-diff shader (wb_diff.comp, which we
  have) in ~25 dispatches a frame. Falls back to copies when its table is full or the GPU lacks the pipeline.
- Where: gpu/vk/vk_memory.cpp 1103-1121 (switch, buffer usage), 3823-3835 and 5041 (call sites), 6201-6345 (the pass,
  ~145 lines). Reborn adds its capture pool's buffers to the same usage (1142).
- Gain: upstream RTX 5080 / 7900X3D, Hyrule Field standing: GPU 1.13 -> 0.34 ms a frame, upload command buffers 1.61 ->
  0.84 ms, all profiled GPU 9.66 -> 9.29 ms; fps 61.7/59.7 vs 59.8/54.0 ("gain not measured"). Mostly a GPU-time cut; our
  Market is CPU-replay bound (so possibly nothing here), but it also replaces ~1,300 recorded copy regions with ~25 dispatches
  on the replay thread and our log's "memory sync" is 1.3-2.7 ms: worth one Market + Kakariko A/B.
- Ours: missing. Default on (`RX_VK_MSYNC_PASS=0` off). Size ~200 lines, renderer only.
- Risk: medium: a sync bug shows as wrong textures or flicker; needs subgroup votes (RDNA4 has them).

### 6. Commit-limit crash fixes (the bundle HeyListen's survey left "waiting") — LATER, bundle with an API bump
- What: (a) renderer holds a 128 MB commit reserve and gives it back from operator new's handler at the commit limit
  (vk_texture.cpp ~379, `RX_VK_COMMIT_RESERVE_MB=0` off with the rule); (b) the page-table flush catches std::bad_alloc and
  writes changes at once (vk_memory.cpp 587-605; upstream #2941: 32 GB RAM + 2 GB page file, game closed loading Hyrule
  Field); (c) a C++ exception escaping the replay is logged with its type and message before it unwinds (vk_replay.cpp 6599,
  "exception 0x20474343" with no clue); (d) a crash at guest 0..1 MB is logged as "out of memory or a bad game file" (mkw_glue.c
  229); (e) the profiler's stack walk survives faults (mkw_glue.c 680; only for sampling tours).
- Gain: crash fixes, no fps. Ours: all missing (we have commit_wait and the out-of-memory box). Hardware: Windows, small page
  files. Not a risk on this PC (32 GB), useful for everyone else. Size ~150 lines. Risk: low.

### 7. Staging arenas made before the game, and a spare kept ready — LATER (A/B camera turns in Kakariko)
- What: making a 64 MB staging arena mid-play took 12-25 ms (Deck; up to 116 ms) on the replay thread when the camera turned;
  now 4 are made at start on an empty device (`RX_VK_STAGING_PREWARM`, default 4) and, on cards that keep 256 MB of arenas (ours),
  one spare is held and refilled by a worker (`RX_VK_STAGING_SPARE`).
- Where: vk_replay.cpp 6537-6541; vk_texture.cpp 624-700 and 788-810.
- Gain: upstream named the "a staging arena of 64 MB took" log lines in Kakariko (2026-11-12); numbers are Deck-only. AMD Windows
  unmeasured. Ours: missing. Size ~120 lines, renderer only. Cost: +256 MB VRAM held early (fine on 16 GB). Risk: low.
  Check our log for "staging arena ... took" lines first: if none, skip.

### 8. Direct-mapped front for texture handle lookups (RX_VK_VIEW_FAST) and the per-draw handle memo — LATER (CPU replay)
- What: (a) a 1024-entry thread-local direct-mapped cache in front of handle_hits, checked by key, slot version, destroy
  generation and texture epoch (vk_draw.cpp 3387-3460, cleared at 5843); (b) a draw's handles evaluated once and reused by
  program_for's variant check and the descriptor build (vk_shader.cpp 822-860, `handle_memo_next`), and still_valid from the
  handles just read (vk_shader.cpp 2040).
- Gain: upstream's stated cost was 0.9 ms a frame of map finds (10,600 lookups, 725 draws); the gain itself is not given.
  After our FlatMap (fa53aad5) the map is already cheaper, so expect less. Unmeasured on AMD.
- Ours: missing (we have HandleTable from fa53aad5). Default on (`RX_VK_VIEW_FAST=0` off). Size ~80 lines, renderer only.
- Risk: medium (a stale view is a wrong texture); our flat-caches A/B showed no change on this PC, so this likely won't either.

### 9. Precompile marker kept when the preparation notes nothing new — LATER (saves start time after every rebuild)
- What: every state-list preparation deleted the "all noted pipelines are in the cache" marker, so each build/update, even one
  changing no shader, made the next start build every noted pipeline again ("Loading pipelines", 44,000). Now only a list
  that adds notes removes it. Also: the preparation run lets each pipeline go once cached (`RX_VK_PREPARE_KEEP=1` keeps; 12 GB
  held on start-mode GPUs) and the session's pipeline-cache play files are merged into one (issue 2579).
- Where: vk_draw.cpp ~2265-2272, ~9916-9925, ~870-960.
- Ours: missing (ours: `remove(precompile_built_path())` unconditionally in state_list_prepare, vk_draw.cpp 2073).
- Gain: start time after rebuilds (the owner rebuilds often). No fps. Size ~60 lines. Risk: low-medium (a wrong marker means
  pipelines built in play: stutter). Needs our make_game/prepare flow checked.

### 10. Sorted GPU-tracked ranges (nvdrv) — LATER (game main thread)
- What: the tracked pools kept sorted (bisection) and merged with the sorted mappings instead of a qsort of all at every submit
  after a pool change (qsort was the main thread's busiest host code). host/nvdrv.c 153-175, 199-230.
- Gain: unmeasured in fps. Our Market is replay-bound, so likely invisible here. Ours: missing. ~60 lines, host. Risk: low.

### 11. Game-code natives: zstd sequence loop and name search (HOS_ZSTD_NATIVE, HOS_NAMES_NATIVE) — LATER, careful
- What: hand transcriptions of lifted f_801102e0 (zstd decode, 89% of ParallelDecompThread in 50-400 ms load frames) and the
  two strcmp binary-search loops in f_805aeea0 (92% of OptimizeChangeBanc arriving at Hyrule Castle), byte-for-byte state,
  `=2` compare modes.
- Gain: load hitches (Hyrule Castle); an earlier whole-frame zstd variant measured nothing on an RX 9070 XT (Hyrule Field,
  63.4/66.0/66.0 vs 62.9/65.1/65.5 fps, klimovich008). Ours: missing.
- **Touches nx2/oot_patches.py** (splices calls into the lifted functions) — the randomizer's file. ~1,000 lines host.
  Risk: medium-high (a transcription bug corrupts loads). Only for load stutter; run the =2 compare and the randomizer guard.

### 12. Freed address regions decommitted; regions committed as mapped (RX_VK_KEEP_FREED, HOS_REGION_COMMIT) — LATER
- What: the game's address regions were committed whole (8 GB of commit; process 29-30 GB after a few areas); now reserve-only,
  pages committed as mapped/first touched, freed regions' uncovered pages decommitted at the next submission.
- Where: host/hos_mem.c 96-260, 340-360; vk_memory.cpp 4639-4700, 6350; vk_internal.h 265; host/rx_backend.c 314 (API change).
- Gain: commit/RAM on 16 GB PCs (hs483: imports refused, then device lost). Not needed on 32 GB. Ours: missing (we only
  have HOS_KEEP_FREED_PAGES). ~250 lines incl. an MKWVK_API_VERSION bump. Risk: medium (first-touch commit paths).

## User-visible settings and features we lack (all upstream Hookshot unless marked)

- Save backups outside the game folder, auto-restore when the save folder is empty (host/save_backup.c, HOS_SAVE_BACKUP*).
  **Check with the randomizer's save layout before taking.**
- Crash window with a redacted report and an independent crash record (hos_crash_dialog.c, hos_crash_record.c, ~2,800 lines).
- Wide-screen HUD layout for non-16:9 pictures (hos_wide_ui.c, HOS_WIDE_UI, HUD ratio limits) and Reborn's vert+ FOV for
  pictures narrower than 16:9 (host/oot_fov.c, Reborn).
- Intel XeSS / XeSS Native AA upscaler (vk_xess.cpp; runtime not bundled). Not useful on this PC.
- CRT filters (crt_lottes / hyllian / zfast, output stage; off by default).
- Frame generation capped to the display's refresh, late generated frames dropped (vk_framegen.cpp 153, 610, 1087;
  RX_VK_FRAMEGEN_UNCAPPED). Worth taking if the owner uses frame generation on a high-refresh display.
- Camera cut resets temporal history (DLSS/FSR/FG smear after loads; vk_temporal.cpp 1253, RX_VK_TEMPORAL_CUT). Relevant to
  FSR 4 Native AA: a one-frame ghost after each load/cut. Small (~60 lines incl. dlss_math.h). Good later pick.
- Rows: Texture detail (Auto/Full/Medium/Low), Threaded rendering (Auto/On/Off), Auto run, Skip title screen (oot_autoload.c),
  Audio Mono, a render-thread lane in the frame graph.
- Settings file in the user folder (options_path.c) so a new build keeps choices; game folder cache/ and logs/ subfolders.
- One game/preparation process per folder (Reborn, host/ocr_instance.h, exit 73 when busy): stops two runs sharing caches.
  Useful for our perf-ab copies only if they share a folder.
- Launcher (Reborn): forest theme, build/start progress screens, Classic UI download. Not applicable (our launcher differs).

## Skipped

- RX_VK_GAME_ORDER (pass/dispatch barriers by the game's own): NVIDIA-only default, GPU time; our frame is CPU-bound.
- RX_VK_READBACK_SEND: acts on held batched submits; batching is RADV/Deck-only by default; no effect on AMD Windows.
- RX_VK_ASYNC_LOAD (program reads off the replay threads): the stall is on PCs under 20 GB RAM; ours has 32 GB and keeps them.
- HOS_BG_CAP (background threads capped): off by default, and no limit on 8+ core hosts (ours: 9800X3D, 8 cores).
- HOS_VCORE_SPIN_US, HOS_VC_PRIO, HOS_VCORE_WAITS, HOS_EVENT_WATCH_LR, RX_VK_RECORD_WORDS, RX_VK_NULL_TEX, RX_VK_SKIP_3D_DRAWS,
  RX_VK_SKIP_HALF_PASS, RX_VK_PASS_TRACE: experiments, diagnostics or RTX 50 hang workarounds, off by default.
- RX_VK_UB_SNAPSHOT_REUSE: only with the uniform snapshot, default on Intel and iGPUs only.
- astc_opaque.h (opaque ASTC kept as BC1, half VRAM): VRAM saving we don't need; conflicts with our AMD BC3 handling.
- RX_VK_DESCRIPTOR_SETS: off by default, a comparison switch.
- RX_VK_NATIVE_NARROW: Intel/Battlemage compatibility; changes the program cache stamp.
- Driver faults kept across runs only on AMD (Reborn): ours already keeps them on AMD.
- Lift change from ProjectReLink (a64_lift.py: A64_VFPX_SUM partial lanes, FPX_EASY_HEADER; third_party/a64-kit): game-code CPU,
  needs a re-lift and the randomizer guard; already on the HeyListen "waiting" list (FP lift switches). Take from ReLink/Hookshot.
- Reborn's dropped fast-float lifter (nx2/fastfp.py) and WebGPU tree: removed in this import; nothing to take.
- Launcher, installer, Classic UI, build art, checksums, VALIDATION docs: packaging only.

## 2026-11-18: do items 2 and 3 touch the Market's 1% low? No (read from our own logs)
In the Market headless bench (6 runs, mkq_mk_on_*, vct_vc_a_*) the slow pool imports (10-25 ms, the 22-25 ms Reborn
measured) all come while the area loads, before the first input; in the measured window (the last 50 s, circling the
square) there are 0-2 imports a run, ~3 ms each. The Market's slow frames (logs/hookshot_frames.csv of the diagnose run)
are bursts when new things come on screen: the game's main thread +6 ms CPU and +9 ms waiting on its workers, our
draw/descriptor/texture work +5 ms, 8x the texture uploads. So items 2 and 3 are for area-entry stutter (worth porting
for that), not the Market's 1% low.
