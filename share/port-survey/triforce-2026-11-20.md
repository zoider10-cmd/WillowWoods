Release notes: there is no changelog entry for 0.6.0 (`changelog.txt` stops at 0.1.0). The release commit's own text:
"Faster frames (the replay's memory work, held submits, helper threads, collection and capture cuts), the game letting old

docs/development.md's switch table (each new switch with its measurements) were the guide used here.

Triforce's numbers come from its "lab" and "the owner's Market spot / save" (the GPU is not named in the diff; several
items cite NX2navi's RX 7900 XT, or tickets on RTX 4090/5090). None is measured on an RX 9070 XT.

Our tree shares the lineage (same file names, `vk_draw.cpp` 11.9k lines against their 12.9k), so most items port as
hunks, not rewrites. Everything below that touches the game's frames needs the Market A/B on this PC before it is kept.

## Ranked candidates

### 1. The game told what memory it really uses, with 1 GB of slack (QueryMemoryInfo) — port first
- **What:** `nn::os::QueryMemoryInfo`'s "used" becomes program + heap + every page the game mapped, less 1024 MB of slack
  (`HOS_MEM_QUERY_SLACK_MB`). The game's Resource Memory allocator sizes its cache from total − used: told the old
  figure it never let an area go (12.5 GB of the console's 9.8 after four areas; 16 GB PCs ran out: tickets "0.5.1
  Memory-Retention Regression", "Ton of performance issues after a certain amount of time playing").
  Second half, needed with it: on Windows, `discard_pages` zeroes pages a Vulkan import holds instead of
  `DiscardVirtualMemory` (the discard gave nothing back there and cost 3.7 ms a region, 42 s on the Resource Memory
  thread over a tour once areas were let go: Hyrule Field 34 fps, Castle Town 15). Linux already zeroed them.
- **Files:** `host/hos_mem.c` (`query_used`, `game_pages_now`, `census_game_bytes`, `discard_pages`).
- **Gain (Triforce lab, same build A/B):** with no slack the game evicted and reloaded in every scene (Kokiri 52 fps,
  Lake Hylia 42, against 60 / 59.5 with the old answer); with 1024 MB slack 60.0 / 59.9 and its memory held at 10.7 GB
  instead of 12.5 and climbing. Zeroing: 5.2 GB zeroed in 0.47 s over a whole tour.
- **Ours:** we have the first half without the slack and switched off. `hos_used_memory` (host/hos_mem.c:349) counts the
  heap and all mapped pages, but 22b8d22d ("Mako 4.1.1 ... new used-memory figure off by default", `HOS_MEMINFO_NEW=1`
  turns it on) turned it off because the Plaine tour ran 57-58 fps against 62. Triforce's finding explains that loss:
  without slack the game evicts in every scene, and the Windows discard of imported pages is slow. Our Windows
  `discard_pages` (host/hos_mem.c ~150) lacks the zeroing; our Linux branch has it.
- **Hardware:** none. Helps low-RAM PCs most; on the owner's PC the gain is steadier memory and fewer slowdowns late in
  long randomizer sessions.
- **Port:** ~60 lines. Add the slack to `hos_used_memory`, the zeroing to the Windows `discard_pages`, then A/B with
  `HOS_MEMINFO_NEW=1` on and off. Does not touch the lift or the randomizer code. Our `mapped_bytes` counts pages
  differently from their census map (a page mapped twice), so check the log's figure against `mem: census`.
- **Risk:** medium. The game now frees and reloads resources (more streaming); our `oot_heap_retry.c` covers the heap
  running full. Check a long play session: memory flat, no new hitches at area loads, no crash at a save load.

### 2. Cheaper foliage in the sun's far shadow cascades (cull + 2x2 shading rate) — port first
- **What:** draws of mesh programs into shadow cascades 1-2 that cull neither face get back-face culling
  (`RX_VK_FOLIAGE_SHADOW_CULL`, default from layer 1); from layer 2, native mesh draws shade at 2x2 with
  `VK_KHR_fragment_shading_rate` (`RX_VK_FOLIAGE_SHADOW_VRS`, default from layer 2). The near cascade is unchanged.
- **Files:** `gpu/vk/foliage_shadow.h` (93 lines), `vk_draw.cpp` (`draw_cull`, `foliage_rate`, pipeline key; 32 places),
  `vk_main.cpp` (the extension and feature; 18 places), tests/test_foliage_shadow.py.
- **Gain:** 18 to 43 fps at Kokiri Forest's entrance on an **RX 7900 XT** (NX2navi 754ded9, the two halves together).
  Triforce did not measure it again.
- **Ours:** absent. We only have the cascade depth bias (`RX_VK_CASCADE_BIAS`, vk_draw.cpp:5629).
- **Hardware:** AMD-measured. VRS needs `pipelineFragmentShadingRate` plus native mesh shaders (RDNA 4 has both). Off
  elsewhere. Both have an `off` switch.
- **Port:** the cull alone is small (dynamic cull mode, no new pipelines): do it first. VRS changes pipeline keys and the
  stage libraries, so the shader preparation runs once more; bigger, do it second. Not the lift, not the randomizer.
- **Risk:** low for the cull: a lone card facing away from the sun loses its far shadow. VRS: coarser alpha cut-out in the
  far cascade only. Compare pictures of Kokiri and the Lost Woods.

### 3. Page touch before a background import (area-change submit stalls) — port first
- **What:** before `vkAllocateMemory` imports a range of the game's memory on the background thread, one byte of each
  page is read outside the driver. The driver otherwise faults in untouched pages inside the call, holding a lock that a
  queue submit on another thread then waits for.
- **Files:** `gpu/vk/import_touch.h` (50 lines), `vk_memory.cpp` `import_pool` / `bg_main`, tests/test_import_touch.py.
- **Gain:** on an RTX 5090, allocating the 288-752 MB ranges went from 16-93 ms to 4-13 ms, and the longest queue submit
  next to an import in play from 71-93 ms to 10-12 ms. Unmeasured on AMD.
- **Ours:** we have the background imports (`bg_main`, `import_pool`, "imported ahead" in vk_memory.cpp:3426) but no
  touch.
- **Hardware:** Windows only; whether AMD's driver locks pages the same way is unknown, so measure it. Switch
  `RX_VK_IMPORT_TOUCH=0`.
- **Port:** ~80 lines; fits our `import_pool`. Not the lift or the randomizer.
- **Risk:** low (it only reads, under the existing fault guard). Measure area-change hitches with the frame log.

### 4. Fog's dark trails fixed (volumetric fog's first pass computes every froxel) — port first (visible fix)
- **What:** the fog's first compute pass skips froxels behind last frame's coarse depth, and the history smears them into
  dark trails beside near objects, worst at screen edges in the Lost Woods and Kokiri Forest. The one comparison is made
  never true by a SPIR-V matcher at `make_module`, outside the translation stamp, so no program is translated again.
- **Files:** `gpu/vk/spv_fog.h` (401 lines), `vk_shader.cpp` / `vk_draw.cpp` (kFogPatch in the precompile record),
  tests/test_spv_fog.py and .cpp. After NX2navi 0379b00.
- **Gain:** visual. A little more GPU time in that pass (unmeasured).
- **Ours:** absent (no froxel or trail fix in gpu/vk; our `make_module` is in vk_shader.cpp).
- **Hardware:** all GPUs. `RX_VK_FOG_CULL=1` puts the game's behaviour back.
- **Port:** ~450 lines with tests, mostly self-contained. Only that one compute pipeline is new to the driver cache.
- **Risk:** low: the matcher refuses a near miss and logs it. First check that our build shows the trails (move the camera
  fast past a tree in the Lost Woods).

### 5. CPU cuts per frame in the replay ("collection and capture cuts") — later, one at a time
Each one has its own default-on switch in Triforce. All touch our heavily changed `vk_memory.cpp` / `vk_replay.cpp`, so
each is a medium-size hunk that needs a Market A/B on its own:
- **Held submits' copies left behind** (`RX_VK_HELD_BEHIND`) and **held submits** (`HOS_NVN_HOLD=2`, host/nvn_native.c):
  the main thread's two submits a frame are replayed by a host thread, which takes 3.4-4.8 ms of capture and replay
  off the main thread at the Market. Measured at Triforce's Market spot, 3+3 rounds: 76.2 -> 77.1 fps, **1% low 57.2 ->
  59.2**. Ours has only the old `HOS_NVN_HOLD=1`. Largest of these, and the riskiest: about 0.14% of pages are rewritten
  between submit and capture, and it interacts with the virtual-core and lock order (`flush_cs`). The 043db52 Linux fix
  belongs to it.
- **Late pages' wait moved to the queue** (`RX_VK_LATE_QUEUE`): 79.8 -> 80.4 fps, frame log clean. Depends on our
  late-fix path (`RX_VK_LATE_FIX`, which Mako 4.1.1 turned off), so check first whether it applies to us at all.
- **Fast fence poll + readback ticket** (`RX_VK_FENCE_POLL_FAST`, `RX_VK_READBACK_TICKET`): the main thread's
  `nvnSyncWait` polls stop waiting ~1.4 ms a frame behind the Presentation Thread's replay lock. Unmeasured in fps.
- **Mirror sync walk** (`RX_VK_MSYNC_FAST`): 0.86 -> 0.45 ms a frame (measured "elsewhere").
- **Wide thread-local pool table** (`RX_VK_TL_POOLS_WIDE`): ours still has `tl_pools[1024]` (vk_memory.cpp:3389), the
  size Triforce replaced. Helps only the parallel replay, which is off by default here: low priority.
- **Occlusion reports in a flat map** (`occ_answer.h` with `FlatU64`): 0.76 ms a frame of the Presentation Thread at
  ~2,600 reports a frame. Ours keeps its occlusion state in vk_replay.cpp:425ff; check whether we allocate a node per
  report before porting.
- **Collect fast** (`RX_VK_COLLECT_FAST`, host/rx_backend.c): unaligned loads at range edges. Unmeasured.

### 6. OptimizeChangeBank throttle (HOS_BG_THROTTLE, default 300 us run : 3 ms sleep) — later
- **What:** OoT's lowest-priority background thread runs without end on PC (35-44% of a logical processor in busy
  places) and slows the game thread on the same core's other SMT half by up to 1.7x. Throttled at an nn::os or SVC
  checkpoint, it uses ~5-9% of a processor.
- **Files:** `host/hos_thread.c` (`bg_throttle`, `bg_kind`).
- **Ours:** we only lower its priority (`THREAD_PRIORITY_LOWEST`, host/hos_thread.c:1114, `HOS_OCB_NORMAL`). No
  throttle.
- **Gain:** no fps figure in the diff. The Ryzen in the owner's PC has SMT, so this may help 1% lows.
- **Port:** ~60 lines. **Randomizer check:** this thread rebuilds model material blocks (oot_heap_retry.c). Slowing it
  could delay a model or material change, so try equipment and tunic swaps and the gift-item models.

### 7. Shader-cache upkeep: lib check, checkpoint saves, carry over an update, kept set — later (owner's time, not fps)
- **lib_check** (`gpu/vk/lib_check.h` 160 lines, after NX2navi e10ef60): at start, 12 stage libraries are sampled. If more
  than half are cold (lost or refused `*_pipelines.bin`), the driver's part is made again before the game, instead of
  draws waiting in play. NX2navi measured cold libraries on an RX 7900 XT at 93/242 ms each: a village walk skipped
  11,180 draws, with waits of 1-2 s. This one prevents stutter. Ours has the prepare record (`hookshot_prepared.bin`,
  `kWarmRecipe`) but no check.
- **warm_checkpoint** (`warm_checkpoint.h` 113): saves the pipeline cache every 10 min during the ~2 h AMD preparation, so a
  crash or reboot does not start from nothing.
- **pcache_carry** (`pcache_carry.h` 237): carries `mkw_vk_pipelines.bin` over a translator update, capped at 1.25x its
  base. An update's warm took 5608 s against 16 s with the cache. Useful here: every translator change we make
  re-prepares for hours on the 9070 XT.
- **cache_set** (`cache_set.h` 275 + `vk_cache_set.cpp` 133): keeps one earlier set when a setting changes the stamp
  (mesh shaders row, Robust buffers), so switching back costs nothing.
- **Port:** all in `vk_draw.cpp` (prepare, `pipeline_cache_save`), with their own tests. Take lib_check first, then carry.

### 8. Crash report with every thread's stack; hang report on demand — later (small, helps rando bug reports)
- `host/crash_threads.c/.h` (176 + 57; `HOS_CRASH_THREADS`, Windows): a crash report ends with one line per other thread
  (module + offset). It was made for the crash while a save loads.
- `vk_hangdump.cpp` + `hang_watch.h`: putting a file `<report>.now` in the game folder makes the hang watch write every
  thread's stack within a second. It is for a loading screen that never ends while frames still show, which the stall
  watch misses.
- `RX_VK_SLOW_TAKE_MS` (20 ms default): a log line breaking down any slow submit-time capture (ticket "Heavy Stuttering in
  Hyrule town").
- Ours: `vk_hangdump.cpp` has the stall watch only; `hos_crash_record.c` logs the faulting thread only. ~300 lines in all,
  diagnostics only, no game behaviour.

### 9. Sharpness applied to the 3D before the HUD, and FSR 3.1 sharpness boost — later
- `gpu/vk/sharpen_rules.h` (218): with DLSS or FSR the Sharpness row uses the upscaler's own sharpening (FSR 4's, FSR 3.1's
  RCAS) on the 3D before the HUD, not on the whole window. HUD text is no longer sharpened. Below 3/4 render scale FSR
  3.1 gets extra sharpness (NX2navi 385734d). LOD bias in quarter levels.
- Ours: FSR 4 sharpening is off (`d.enableSharpening = false`, vk_fsr4.cpp:1173, "the Sharpness row sharpens at the
  window, after the HUD"). We already have a LOD bias (`RX_VK_UPSCALE_LOD_BIAS`). Visible to players with FSR 4 on;
  check what the owner uses.

### 10. Upscaler failure retry (FSR 4 / DLSS) — later, small
- `temporal_rules.h` (FSR4-1, NX2navi b5789c6): if creating or evaluating the upscaler fails (VRAM full while an area loads),
  the game's own upscale is used for 2 s, then the upscaler is tried again; after 4 failures in a row it stays off until
  the row is set again. Ours gives up on the first failure in places (vk_fsr4.cpp:663 "A failure is not tried again").
  ~140 lines.

### 11. Controller fixes — later, small
- Guitars and drums seen as an Xbox 360 pad through a generic driver are left out of the game's input (ticket "Controls
  not working properly", host/pad_sdl.c). Button prompts on Auto remember the device used last (`prompts_auto.txt`).
  Controllers are scanned every quarter second at start.
- Per-stick dead zones (Left/Right 0-50%) in place of one Stick dead zone row. Ours has one row (vk_menu.cpp:2050).

## Settings and features Triforce has that we lack
- Per-stick dead zones (above). Output resolution 5120x2160, and a handheld 1536x864 entry on the same row (ours keeps a
  separate Handheld profile).
- Menu rows grouped under the game's separators, and rows that do nothing with the current settings hidden (Paper white
  with HDR off, the DLSS model without DLSS). Merged rows: HDR Off/Expanded/Native/Native+RenoDX, Frame pacing
  Off/Even/Steady, Low latency (Reflex or Anti-Lag 2 in one row). A presentation idea; our menu differs, so it is not
  a port.
- Steady frame rate (`HOS_FPS_STEADY`, existed in v0.5.2): pacing to a rate the PC holds in the scene. Not for 120 fps
  VRR play; skip unless the owner asks.
- Benchmark tour skips a place it cannot reach instead of failing (host/hos_bench.c). Only relevant if we take the
  benchmark mode (not taken on 11-19).

## Launcher ideas worth copying into ours (launcher/Launcher.cs)
- **Build time shown from this PC's last builds** (`launcher/Logic/Build/BuildTimes.cs`: "about 45 minutes", or a
  stated range by CPU threads when there is no history; stage times kept in `launcher_stages.json`). Useful for our
  rebuilds.
- **Music from the player's own game files** (docs/launcher-music.md; `Core/GameFiles/Bwav.cs` decodes BWAV to WAV in
  %LOCALAPPDATA%, nothing shipped). Saria's Song, Temple of Time while building, the item fanfare when done. Nice, but
  cosmetic.
- **Color scheme picker** (docs/launcher-color-scheme.md, `LauncherColor.cs`). Cosmetic.

## Skipped
- `RX_VK_ASYNC` replay-thread rules (async_rules.h): off by default; open bug (Link drawn black for a frame).
- Parallel replay early segments / segment_plan (`RX_VK_SEG_EARLY` measured 79.0 -> 70.9 fps, off) and the helper
  threads' default back to 2-3: ours keeps the parallel replay off.
- `redrawn.h` window (the 0.5.2 stutter): fixes Triforce's own v0.5.2 rule, which we never took.
- `oot_tex_compact.c` / patch_tex_compact: we already have it, and ours paces it by default (`HOS_TEX_COMPACT_MS`, 1000 ms).
- `RX_VK_TEX_WARM` (textures uploaded during loading screens): off by default and unproven there; revisit if area-change
  first frames (100-180 ms) remain after items 1 and 3.
- `HOS_MEM_LIMIT`, `HOS_MEM_TRACE`, region-free-without-discard: lab tools; `=1` hung a save load.
- NaN selects (`spv_nan_select.h`): AMD's older compiler on RX 5000/6000 only, not the 9070 XT. Worth it only for
  releases to such players.
- AMD integrated-GPU mirrors, memory trial (`test_memory_trial.py`): our sparse mirrors are off by default.
- GPU device chosen by name (`gpu_choice.h`): laptops with two GPUs.
- AMD FSR 3.1.6 frame generation on RX 6000/7000 and HUD-less input for AMD's FG: we have Redstone FSR 4 FG with its
  HUD-less picture already (vk_fsr4.cpp `redstone_hudless`).
- FG own motion (`RX_VK_FG_OWN_MOTION`), DLSS frame generation rows, Reflex frame limit: NVIDIA, or covered by ours.
- `EDEN_NX2_GM_LEAN`: off by default; retranslates every program.
- Title-screen Mods entry, text_spread, focus/mods animations, game_grid: Triforce's own menu and mods UI.
- launcher/ (web UI, Build protocol b0e46ad, Release, Linux platform), builder/: launcher-only.
- 043db52, scripts/linux/*, AppImage: Linux-only.
- Robust buffers / mesh-shader rows' cache set beyond item 7, readme and docs text: nothing to port.
