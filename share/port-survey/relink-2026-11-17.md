## Candidates, best first

### 1. A draw with no pipeline yet is left out only where the next frame draws it again (9fc9a83): port first
- What: today a draw whose pipeline isn't ready is left out when its targets already hold an earlier frame's picture
  (`targets_persistent`). That's fine for the scene, which is redrawn every frame. It's wrong for a piece the game draws
  once into a target it keeps (a tile, a decal, a cached shadow): that piece is never drawn again, and the old texels
  stay until the area reloads ("striped ground", ReLink issue 47; a Fire Temple route showed it every time). New
  `targets_redrawn()`: the draw may be left out only if every target was drawn last frame and the viewport and scissor
  cover 90% of the target. Other draws wait for their pipeline. It also logs the first 40 draws left out and the first
  40 waited for.
- Files: gpu/vk/vk_draw.cpp, +38 lines.
- Gain: a correctness fix, not speed. ReLink didn't see the stripes on its own PC either (its pipelines were ready).
- Ours: we have the same exposure. vk_draw.cpp ~7590 leaves a draw out when
  `!always_wait && targets_persistent(at) && !writes_memory(p)`, and nothing checks whether the target is redrawn.
  Owner's logs: 2,761 frame lines, 23 with draws left out (0.1-1.9 a frame). Rare on a warm cache, but not zero.
- Hardware: none. On AMD the cost is a few more short waits on first visits, only for partial draws into kept targets.
- Default on; ReLink's `RX_VK_SKIP_PARTS=1` restores the old rule.
- Size: small (one function and one condition, plus a log). Doesn't touch the randomizer or the lift.
- Risk: low. Worst case, a few draws wait instead of being left out, so a small first-visit hitch.
- Score: **port first** (cheap, fixes a real visual bug class, costs nothing measurable on a warm cache).

### 2. Uniform buffers bound straight from guest memory copied into the recording (30d7df1, #102): later, behind an A/B
- What: a uniform buffer bound from a pool that has no VRAM mirror aliases guest RAM. The game can rewrite it after the
  present while the GPU still reads the frame before, which shows as one-frame flicker or wrong matrices. Such bindings
  are now copied into the recording's stream; mirrored pools stay zero-copy. A 4096-entry table per recording copies
  each range once until an update, burst submit or CPU fallback write bumps a generation. New
  `gpu/vk/direct_ub_snapshot.h`, a `direct` flag on BufferRef, and `ub_gen++` on the CPU fill/copy paths in vk_replay.cpp.
- Gain: author measured only on Linux BC-250 (45.5 fps over a 220 s route, no device loss); no before/after number.
- Ours: partly. We have `RX_VK_UB_SNAPSHOT`, but all-or-nothing and on by default only for Intel without mirrors
  (vk_draw.cpp ~3443). The owner's log has the mirror on, but pools are bound direct until their mirror is made, and
  also when refused, "WANTED" or retired. Those are the cases this covers.
- Hardware: matters most where there is no mirror (APUs, Deck, GCN). On this RX 9070 XT, few bindings are direct, so
  the cost should be small, but it sits on the replay's hot path (`uniform_range`).
- Default on (automatic); `RX_VK_UB_SNAPSHOT=0` gives direct bindings, `=1` copies every UBO.
- Size: about 270 lines with tests; vk_draw.cpp, vk_memory.cpp, vk_replay.cpp, vk_internal.h. No randomizer or lift
  files.
- Risk: medium. The hot path could cost replay time, and the generation bumps have to cover all of our write paths.
- Score: **later**. Port it, then run a Kakariko A/B (the replay is half the frame there) and keep it only if it's no
  worse. Count first how many UBO binds are direct in the Market (a counter on `b.direct`).

### 3. RX_VK_PROF_FINE=1 times draw preparation, command totals and mesh-draw parts (07d0988, #108): later (diagnostic)
- What: the per-frame fine line adds draw preparation (targets, program pick, pipeline lookup), descriptor and command
  totals, and the mesh draw's parts, with counts of mesh, indirect, counted and nonzero-first draws. "Total minus
  sections" shows time no timer covered.
- Gain: none (diagnostics). Their finding on RADV BC-250: about 1 ms a frame of unattributed replay time was almost all
  the direct `vkCmdDrawMeshTasksEXT` recording.
- Ours: we have RX_VK_PROF_FINE with our own kFineT/kFineC tables (layout differs), so this is a hand port.
- Why it matters here: the Market frame is limited by the replay (~9 of ~14 ms). This tells where in `draw()` the time
  goes on AMD Windows before choosing the next cut.
- Default off; each site tests a constant. About 90 lines in vk_draw.cpp; nothing else touched.
- Risk: very low. Score: **later**, worth doing before the next replay-cut attempt.

### 4. RX_VK_DEFER_MAIN_REPLAY=1: a non-presenting thread's submits replayed on a worker of their own (3fef7ed, #82): experiment only
- What: submits from threads that don't present are still captured and ordered at once, but replayed on a dedicated
  "mkw_vk main-sub" thread (above normal priority). Waits, drains, settles and presents let it catch up first. Also
  splits `q_last` / `value_queue` under a new small lock (`q_map_mu`).
- Gain: the author's BC-250 number reads "37.55 against 39.20 fps" without saying which side is which. Likely no gain,
  possibly a loss; Linux only.
- Ours: not present. Our vk_replay.cpp has the same `sync_order_mu` / `qruns` structure, so it should apply with some
  adaptation.
- Default off. About 130 lines in vk_replay.cpp. Doesn't touch the randomizer.
- Risk: medium (ordering and locking in the replay). It only helps if a real share of the Market's replay comes from
  non-presenting threads. Check that first: per-thread submit counts in one Market log.
- Score: **later, experiment**. Port only if that count says a few ms could move, then A/B (Kakariko first).

### 5. "30, smooth": the start-up screen presents in the usual mode, not FIFO (7b110a2, #93): later, small
- What: with the 30 fps cap the swapchain was FIFO from the start. On AMD (no separate present queue, 3 images), each
  start-up-screen present held the queue for a refresh, and shader preparation stalled (RX 6600 XT: stuck at
  ~1600/38809 for 5+ min). Now the start-up screen uses the usual mode, and FIFO comes back at the game's first frame.
- Ours: we pick FIFO only for V-Sync On (vk_main.cpp ~892-915) and use immediate on AMD otherwise. The stall could hit
  us only with V-Sync On (or RX_VK_FIFO=1) during a full shader prepare on AMD. Not verified.
- Size: about 18 lines in vk_main.cpp; AMD-specific benefit. Score: **later** (check first that V-Sync On plus an empty
  shader cache really stalls on this PC).

### 6. HOS_MEMINFO_MAPPED=1: the game's mapped pages count as used memory (b4b646d, #77): later, for low-RAM PCs
- What: QueryMemoryInfo and GetInfo 7/22 count pages mapped through AllocateMemoryPages, so the game stops growing its
  caches past the console's budget. Uses a lazy bitmap, cleared on FreeMemoryPages and FreeAddressRegion.
- Gain: author on BC-250 Linux, one pair: peak memory 8.05 -> 6.87 GB, swap 5.8 -> 0.6 MB, fps 38.0 -> 37.1.
- Ours: not present (host/hos_mem.c, hos_svc.c).
- Hardware: helps 16 GB and lower PCs; it trades about 2% fps for RAM. Nothing to gain on a PC with plenty of RAM.
- Default off. About 190 lines including the test. Host only, not the randomizer's files.
- Score: **later**. Useful for players with less RAM than the owner, not for this PC.

### 7. F12 saves a screenshot of the game's picture (56fee7f): later (feature we lack)
- What: the presented picture at the game's output resolution (HUD in; menu, FPS counter and scaling out) is read
  back and written as a PNG to the game folder's `screenshots` (WIC on Windows) by its own thread, with a notice on screen.
- Ours: no game-picture screenshot key; we have HOS_HEADLESS / RX_VK_SHOTS for test runs only.
- Size: about 224 lines (new vk_screenshot.cpp, plus vk_replay.cpp and vk_menu.cpp). vk_menu.cpp carries our
  randomizer settings, so merge carefully. Score: **later** (user-visible convenience, no risk to play).

### 8. More device-lost markers: uploads, command buffer start and end, present, read-backs (b66d8da): later, only when needed

- Ours: has RX_VK_CHECKPOINTS, but not these kinds. Diagnostic, off by default, about 90 lines across 6 files.
- Score: **later**, only if a device lost shows up on this PC again.
