## Ranked candidates

### 1. No-code A/Bs: switches we already have, which Longshot measured cutting long frames - TRY FIRST (today, no build)

From deb08f36's "Works well together with" (Windows 11, RTX 4070 SUPER, Ryzen 9 9900X, Castle Town market walk, cap 90,
two runs each; measured on an earlier head):
- **`HOS_KEEP_FREED_PAGES=1`**: the frames where the game's main thread is blocked a whole frame while freed memory is
  given back to Windows: 15-25 a Market visit -> 0; frames over 25 ms 29-50 -> 12. Costs 0.5-0.7 GB RAM in use. **We have
  the switch** (host/hos_mem.c, off by default). Our 52a92f5e already gives the virtual core up during that discard, so
  the gain here may be smaller, but this is aimed squarely at the 1% low. Reborn's RAM test said short RAM did not lower
  the 1% low, so the 0.5 GB is affordable.
- **`RX_VK_FRAME_GATE=0` + `RX_VK_READBACK_LATE=3980,9b040,8b040,44b040,1b580`**: the game neither waits for the renderer
  before its next frame nor for those GPU results (ranges of those byte sizes read a frame old). Frames over 20 ms 355/411
  -> 169/211 on their main; +1.9 fps. **We have both switches** (gpu/vk/readback_late.h, vk_replay.cpp; FRAME_GATE only
  matters with the render thread on, which Auto turns on at 16 logical processors). Picture risk: our docs call
  FRAME_GATE=0 "a test" (it once drew the lit scene black for one frame), and READBACK_LATE hands the game one-frame-old
  GPU results. A/B each separately, look at the shots. `RX_VK_READBACK_LATE=newest` is the rule our docs measured.
- Bench: the Market A/B (5 reps; these are tail changes, so read the 1% low and worst frame, not the mean).

### 2. Lifted stores mark only GPU pages, by a page bitmap (35a4a9fc, #1617; RX_MARK_BITMAP) - PORT FIRST (code)

- What: every store of the translated game writes a page mark (A64_MARK: two byte stores into a64_dirty) so the renderer
  can find what the game changed. The renderer reads only GPU pages' marks. A 16 MB bitmap (one bit per 4 KB page, ~210 KB
  touched) is set by nvdrv.c `map_add` when a GPU mapping is made (va == guest) and for the page before it; A64_MARK
  then marks only when the store's first byte is on such a page. Host writes keep marking every page.
- Measured: Windows 11, Ryzen 9 3900X, RTX 3080 (CPU-bound): Market median 30.9 -> 34.3 fps (+11%), game threads 31.1 ->
  28.5 ms; **Market p99 72.8 -> 57.6 ms, frames over 50 ms 139 -> 54** (a tail gain, unlike the locals). Hyrule Field +6%.
  ballotstomper on Linux (Ryzen 5 5600X, RX 6750 XT): Market walk 40.4 -> 46.1; with every bit set (HOS_MARK_BITMAP_ALL=1)
  41.3, so the bitmap is the gain. **But**: the measured builds also carried other changes (#1560, #1469 locals, a zstd
  branch), the picture was never compared, and no game-free check covers it.
- Ours: **missing** (nx2/rtgen.py MARK_NATIVE_64 marks every store; host/nvdrv.c map_add sets nothing; no
  host/mark_bitmap.c).
- Switch: build time `RX_MARK_BITMAP=0` off (default on there); run time `HOS_MARK_BITMAP_ALL=1` = every bit set, the
  A/B's control in one build. Keep both.
- Size: ~33 lines host/mark_bitmap.c, 2 lines host/nvdrv.c, ~10 nx2/rtgen.py (an `#if defined(A64_MARK_BITMAP)` form of
  A64_MARK), ~5 nx2/build.py. No switches.def here. No API bump.
- Randomizer: not a randomizer file, but every lifted file recompiles (the runtime header's macro changes): a full
  compile, not a re-lift. Our oot_patches.py inlines `A64_MARK(_a, 4)` in one patch (line 85): it follows the macro.
- Risk: **medium, correctness**: a store to a page the GPU reads through a mapping whose GPU address differs from the guest
  address, or a mapping map_add doesn't see, is no longer marked and draws stale. Compare shots (Market, Kokiri, a
  cutscene, a menu, a load) with `HOS_MARK_BITMAP_ALL=1` against default in the same build, then the Market A/B.
- Why here: the only Longshot change aimed at the game threads' time that also measured a cut in long frames, and cheap.

### 3. Translated code: guest registers as C locals, five vector forms as one SSE instruction (deb08f36, #1576) - PORT (in two steps)

- What, two independent pieces in the lift (nx2/):
  - **Vector rewrites** (nx2/fastvec.py, 276 lines): TBL (2,995 sites), EXT (29,451 sites), 128-bit vector loads, DUP and
    FMUL by element: from byte loops through the stack to one SSSE3/SSE instruction each. Game work without them 15.46 ms,
    with both pieces 14.27 ms: **~1.2 ms a frame** in the Market (one run each). Lift switches `A64_NO_VBYTES/VMOVES/VFPX_ELEM=1` turn each off.
  - **Locals** (nx2/guest_locals.py, 255 lines + nx2/ran_funcs.txt, 77,725 guest addresses): a function's 6 most-used
    registers and N/Z/C/V as C locals (the kit's A64_LOCAL_REGS=6 / A64_LOCAL_FLAGS, which our a64-kit already has, off),
    only in functions a 100-minute play session ran. A function the patches touch (`oot_patches.touches()`: runs
    patch_file/output_size_file on its text), one holding an address oot_patches.py names (`mentioned_addresses()`), one
    with spliced C, or one entered below its first block keeps the context. Without them 15.64 ms: **~1.4 ms a frame**.
- Measured: Windows 11, RTX 4070 SUPER, Ryzen 9 9900X, Castle Town market route, 2 runs a side (not interleaved): fps
  56.7/56.3 -> 61.3/60.9, game work 16.60/16.70 -> 14.26/14.58 ms, **1% low 26.2/28.2 -> 27.5/28.1 (no change)**. Standing,
  720p uncapped: Market 72.2/70.9 -> 81.9/82.1 (+15%), DM Trail +15%. Steam Deck +7% where the CPU limits. **The merged
  head (locals only in ran_funcs.txt functions) was built and run by nobody.** Build 12-26% longer before the gate.
- Ours: **missing** both (no nx2/fastvec.py, guest_locals.py, ran_funcs.txt; A64_LOCAL_REGS unset). Our nx2/lift.py has the
  same install chain (insn, fastfp, dead_flags, walk, lift_fixes), so the wrappers fit; their oot_patches.touches() calls
  `patch_file(text, "", True)`: ours has `patch_file(s, name, protect_hearts=False)`.
- Randomizer: **high attention**. Locals change the text every patch anchors on, unless the function keeps the context.
  touches() must ask *every* patching path our build runs (all the randomizer's patches, not only patch_file and
  output_size_file): check chunks.edit_c's callers, and run the rando guard + rebuild.sh's patch count with locals on.
  Vector rewrites don't change what patches anchor on except in a patched function that contains TBL/EXT etc. (rare;
  the guard's patch count shows it).
- Size: ~600 lines of Python + tests + the 77,725-line address list. A full re-lift and compile (their Test Farm: 593 s ->
  ~670-748 s).
- Order: **vector rewrites first** (smaller, no patch interplay, SSSE3: the 7800X3D has it), then locals.
- Why not first: a mean-fps gain that did not move the 1% low in their runs, a re-lift, and the randomizer patch risk.
  But it is the largest measured cut of the game work that our Market is limited by.

### 4. The game's job barriers wait on their mask word, not 20 us sleeps (10fab152, #1662; HOS_OOT_BARRIER_WAIT) + YieldThread keeps the processor (d10b62b3, #1663; HOS_OS_YIELD) - PORT, A/B

- 10fab152: three parallel-for jobs (f_800998a0 the drawing-command job, f_800738e0, f_8007e200) sleep 20 us and look
  again until their masks fill; the main thread is one of the waiters. A lift patch (oot_patches.py `patch_barrier_wait`,
  178 lines) makes the sleep `WaitOnAddress` on the polled word (1 ms cap) and each OR into it wake the waiters.
  host/oot_barrier.c/.h new (~230 lines). Default on (`=0` the sleeps).
- d10b62b3: `nn::os::YieldThread` did `hos_vcore_yield(); SwitchToThread();`; now only the virtual-core hand-over
  (`HOS_OS_YIELD=1` as before). One line in host/hos_thread.c. Ours: identical old form (hos_thread.c:1340).
- Measured: Windows 11, RTX 4070 SUPER, Ryzen 9 9950X3D (SMT off), Market standing, in-run A/Bs: **4 cores** -3.2% frame
  time (barrier; frames >= 16.7 ms 30 -> 19%) and -2.1/-1.7% (yield); **16 cores no difference** for either.
- Ours: both missing. Our case differs from their 16-core one: on 16 logical processors our game's sub-ms sleeps poll
  with SwitchToThread and **at most 4 threads poll at once (HOS_SHORT_SLEEP_POLLERS default threads/4); the rest wait on the
  high-resolution timer, ~0.5 ms late** (hos_thread.c sleep_ns). A barrier sleeper that lands on the timer is exactly the
  late wake this fixes. Reborn's poller A/Bs (4/8/all) showed nothing, so expect little, but it is the one mechanism
  that ends the wait when the work is done.
- Randomizer: 10fab152 **touches nx2/oot_patches.py** (a new patch on three job functions none of our randomizer patches
  name: grep found none); rando guard + patch count ("job barriers were found in N of 3 functions" warning).
- Risk: medium (barrier), low (yield). Both are runtime switches, so one build A/Bs both.
